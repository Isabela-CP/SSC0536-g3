## 🏗️ Arquitetura e Componentes
✅ **Decisões acertadas:**
- **Refatoração para `operations.py`:** A criação de um módulo para validações reutilizáveis (e-mail, campos, tipos) limpa significativamente os controladores (`main.py`), centralizando regras de negócio e reduzindo duplicação.
- **Isolamento de Views:** A criação de `read_views.py` para o dashboard e auditoria mantém a separação de conceitos, permitindo que a lógica de consulta seja testada sem passar pelo overhead do framework HTTP.
- **Flexibilização de busca:** O uso de `re.sub(r"\D", "", term)` no backend para tratar CNPJs com ou sem pontuação é uma excelente prática de UX para filtros de pesquisa.

## 🟡 Não bloqueia
- **Documentação de Erros:** O código introduziu uma hierarquia de erros (`InventoryError`), mas como o `OpenAPI` original não estava documentado para estes novos estados, notei que a documentação da API pode estar ligeiramente defasada em relação ao comportamento real. Isso não bloqueia a funcionalidade, mas vale uma revisão na doc futura.
- **Persistência de Arquivos:** Conforme observado no `backend/README.md`, os binários de relatório ainda são mantidos em memória no dicionário `REPORT_FILES`. Para fins de um projeto de demonstração, isso é aceitável, mas requer atenção em cenários de alta concorrência caso o servidor escale.

## ℹ️ Para registro
- O PR altera estruturalmente como o `login` e `logout` lidam com tokens (passando a gerenciar o `token` via `uuid4` dinâmico), o que resolve problemas de estado persistente que poderiam ocorrer na versão anterior.
- A conformidade visual com o Figma e a interface do usuário não foram avaliadas nesta revisão, pois o diff foca exclusivamente nas alterações de backend que viabilizam o consumo pelo frontend.

> **Nota:** As alterações foram analisadas sob o prisma da manutenibilidade e resiliência do backend para o suporte ao novo frontend de inventário. A refatoração das rotas de autenticação e perfil traz mais segurança e corretude.
